# AgenticDB Safety & Governance Model

## 1. Safety Philosophy

An autonomous DBA must never compromise production data integrity, system availability, or customer security. AgenticDB operates under a zero-trust safety framework combining AST-level query validation, read-only query execution sandboxing, strict action classification, and mandatory human approval gates for persistent modifications.

---

## 2. Action Classification Framework

Every candidate action generated by the AI agent or user is tagged into one of three action classes:

| Class | Description | Autonomous Execution? | Examples |
|---|---|---|---|
| **Class A** | **Read-Only / Non-Mutating** | ✅ Yes | `SELECT`, `EXPLAIN`, `EXPLAIN QUERY PLAN`, reading system catalogs (`sqlite_master`, `pg_stat_statements`). |
| **Class B** | **Ephemeral / Test Workloads** | ✅ Yes (in sandbox) | Running benchmark iterations on temporary copies, dry-run query tests, memory estimates. |
| **Class C** | **Persistent Changes** | ⚠️ **Requires Human Approval** | `CREATE INDEX`, `DROP INDEX`, schema migrations, `VACUUM FULL`, `ANALYZE`. |

---

## 3. SQL Validator & Sandbox Enforcements

The SQL Validator (`app/safety/sql_validator.py`) inspects all incoming SQL statements prior to database dispatch:

1. **AST Parsing (`sqlglot`)**:
   - Parses the SQL statement into an abstract syntax tree.
   - For user query executions, only single statements of type `exp.Select` are permitted.
   - Rejects multi-statement chains (e.g., `SELECT 1; DROP TABLE...`) to eliminate SQL injection vectors.

2. **Keyword Blacklist**:
   - Forbids destructive keywords in interactive queries: `DROP`, `TRUNCATE`, `ALTER`, `GRANT`, `REVOKE`, `DELETE`, `UPDATE`, `INSERT`, `LOAD DATA`, `EXEC`, `ATTACH DATABASE`.

3. **Row Limiting (`LIMIT` Clamping)**:
   - Queries without a `LIMIT` clause automatically have `LIMIT 10000` appended.
   - Queries with a `LIMIT` exceeding `MAX_QUERY_ROWS` (default 10,000) are clamped down to prevent out-of-memory crashes on large datasets.

4. **Execution Timeout**:
   - Every query runs with a strict statement timeout (`QUERY_TIMEOUT_SECONDS`, default 30s) to terminate runaway queries.

---

## 4. Human-In-The-Loop Approval Gates

When AgenticDB identifies an optimization involving a Class C change (e.g., creating an index):
1. The optimization status is set to `pending`.
2. An approval ticket is written to the `approvals` table with:
   - **Proposed SQL Statement**
   - **Action Class (C)**
   - **Expected Performance Gain**
   - **Risk Assessment & Storage Footprint**
   - **Rollback SQL Statement** (e.g., `DROP INDEX IF EXISTS idx_name;`)
3. The operator reviews the proposed change on the **Approvals** page in the UI.
4. If approved: the agent executes the migration and verifies results.
5. If rejected: the ticket is closed with operator feedback stored in the incident log.
